# Session workspace и предметная панель

ACP-сессия в Brigade — это один разговор, которым управляет host. Предметный плагин
добавляет к нему MCP tools, developer instructions и необязательную панель, но не создаёт
второй клиент или второй разговор.

## Компоновка

Web-оболочка следует одной композиции:

```text
SessionWorkspace
└── AcpSession(pane)
    ├── AcpThread
    └── aside: optional pane
```

`AcpThread` монтируется всегда и владеет историей, composer, permissions, моделью и
настройками ответа. На desktop `aside` находится справа. На mobile чат и панель
располагаются один под другим. MCP App рендерит только предметный интерфейс внутри pane.

Здесь mobile означает web-интерфейс с узким viewport. Kotlin Multiplatform client пока
не реализует предметную pane.

Такое разделение сохраняет один источник истины для разговора: MCP App не копирует
историю, не синхронизирует собственный composer и не воспроизводит permission flow.

## Создание сессии

Пользователь сначала выбирает тип сессии — CLI или ACP. Для ACP он независимо выбирает
необязательную pane: **Без панели**, CAD, Coder или другой установленный плагин. Pane не
является третьим типом сессии и не конкурирует с ACP.

В открытой ACP-сессии селектор называется **Панель**. Значение без предметного UI —
**Без панели**, а не «Чат»: чат присутствует при любом выборе.

## Идентичность и совместимость

Совместимость сохраняет wire-поля `experience_id` и `experience_version`, владельца
закреплённого bundle в persisted-модели и RPC `SetExperience`. В новой модели эти данные
означают выбранную pane. Переименование полей не требуется и сломало бы старые клиенты.

Manifest также сохраняет `_meta.brigade.experience.layout`. `ParseManifest`
нормализует старые значения `""`, `"full"` и `"split"` в `"split"`; неизвестные
значения отклоняются. Все MCP Apps занимают inline pane, поэтому для режима отображения
host context объявляет только `displayMode: "inline"`.

## Смена предметной области

Смена CAD, Coder и **Без панели** — изменение runtime-конфигурации существующей ACP-сессии.
Она выполняется только для живой persistent ACP-сессии в idle-состоянии:

1. Registry резервирует idle-сессию и разрешает закреплённые ID, версию и владельца bundle.
2. Brigade подготавливает MCP runtime и developer instructions новой предметной области.
3. В local-режиме новый адаптер выполняет strict resume с тем же native session ID. Pin
   сохраняется после успешной инициализации, перед заменой live-клиента.
4. В Docker-режиме Brigade сначала сохраняет новый pin, затем вызывает daemon `Configure`
   со strict resume. При ошибке Brigade возвращает store к предыдущему pin. Если результат
   `Configure` неопределён из-за отмены, timeout или транспортной ошибки, Brigade также
   пытается вернуть daemon предыдущую конфигурацию. Это best-effort компенсация.

Store и daemon не образуют общую транзакцию. Падение процесса между записью pin и
`Configure` может оставить их в разных состояниях; crash atomicity не гарантируется.

Успешный live switch сохраняет native session ID, текущую историю, workspace и
Docker-контейнер. Strict resume не создаёт новый разговор при ошибке `session/load`.
Эта гарантия относится только к live switch: общие legacy-пути restore и revive сохраняют
своё прежнее поведение и могут перейти к fresh session. Их семантика в этом решении не
расширяется.

Горячая смена во время генерации не поддерживается: UI отключает селектор до idle.
Переключение вкладок и результатов внутри одной pane — визуальное действие и не
перезапускает адаптер.

## Граница MCP App

Host bridge передаёт через `structuredContent.brigadeHost` только capabilities
`openResult`, `appendPrompt`, `coding` и `workspace`. Он не публикует snapshots
`generating`, `lastMessage`, `prompts` и `submitMode`.

Стандартный `sendMessage` остаётся доменным действием MCP App и отправляет сообщение в
штатный thread. `brigade.appendPrompt` только дописывает текст в штатный composer без
отправки. `brigade.cancel` временно сохраняется как совместимое host action.

Новые UI-запросы `PluginService.MCP` содержат `expected_plugin` с ID и версией pane.
После ожидания session lock backend сравнивает ссылку с текущим выбором и отклоняет
устаревший запрос. Поле необязательное, поэтому старые клиенты продолжают работать.

## Владение MCP-процессами

Агент и UI используют два отдельных процесса одного MCP bundle:

- Агентский MCP входит в конфигурацию ACP-адаптера. Адаптер владеет процессом и
  подключает его при старте или переинициализации сессии. Ошибки bundle, конфигурации и
  запуска на этом пути не скрываются: без заявленных предметных tools новая конфигурация
  агента не считается рабочей.
- UI MCP принадлежит `plugin.Runtime`. В local-сессии runtime хранится в live-состоянии
  `session.Registry`; в Docker-сессии им владеет `acpdaemon`, а основной процесс Brigade
  обращается к нему через `DaemonPluginMCP`. Этот процесс обслуживает только MCP Apps
  host и не входит в ACP transport агента.

Оба процесса получают один snapshot stdio-конфигурации, workspace и переменных окружения,
но не разделяют память. Согласованное состояние плагина хранится в workspace. Закрытие или
ошибка UI MCP не останавливает агентский MCP и ACP-чат.

## Lazy lifecycle UI MCP

Конструктор `plugin.Runtime` только проверяет и копирует конфигурацию. UI MCP-процесс
запускается при первом `Dispatch`, поэтому сессия и агентский MCP не ждут открытия pane.
Один старт разделяется между конкурентными UI-запросами, а handshake ограничен конечным
timeout.

Ошибка старта возвращается вызвавшему `Dispatch` и показывается внутри pane. Она не
переводит чат или агентский runtime в failed-состояние. Следующий самостоятельный запрос
может начать новую попытку запуска, но исходный запрос не воспроизводится автоматически.
В частности, mutating `tools/call` выполняется не более одного раза и никогда не получает
автоматический replay после ошибки или неопределённого результата.

`Close` помечает runtime закрытым до ожидания незавершённого старта. Если runtime закрыт
до первого `Dispatch` или во время handshake, поздний запрос не запускает и не
восстанавливает процесс. Это исключает resurrection старой pane после смены плагина или
закрытия сессии.

## Legacy MCP Apps

Host не переписывает произвольный legacy HTML. Если старое приложение содержит свой
composer, он останется внутри iframe, но штатный ACP-чат всё равно будет расположен рядом.
Стоковые CAD и Coder не показывают дублирующий ввод. CAD использует стандартный
`sendMessage` только для предметных действий, а Coder вызывает `brigade.appendPrompt`,
когда нужно дополнить штатный composer.
